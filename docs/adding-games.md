# 新游戏接入与旧游戏回归

## 模块边界

- `shared/games.js`：公开的游戏 ID、显示名和模式。不要放后端规则、凭据或运行状态。
- `server/game-rules.js`：按 ID 注册规则。`extendRules` 拒绝覆盖已存在 ID；规则定义和模式数组冻结。
- `server/gomoku.js`、`server/snake.js`：各自的棋盘、胜负、回合等规则。规则只操作传入的房间；禁止操作其他房间、全局状态或进行网络 I/O。
- `server/game.js`：共享成员关系和创建、加入、离开流程；通过注册表调用初始化、认输和再战规则。
- `src/game-views.js`：按 ID 注册 `Card` 和 `Match`。大厅自动列举卡片；弹窗模式来自公开目录。
- `src/Gomoku.jsx`、`src/Snake.jsx`：各游戏独立界面。游戏视图和卡片有错误边界，渲染出错时仍能使用其他入口。
- 身份、会话、Redis 原子提交和房间同步属于共享基础设施，不应为增加一款游戏而重写。

## 新增步骤

1. 使用全新、稳定的游戏 ID，在公开目录增加名称和支持模式，不能复用已有 ID 或改变旧模式语义。
2. 新增独立后端模块，在规则注册表增加 `initial()`、`reset(room)`、`resign(room, userId)`；初始化返回全新对象，不得含共享数组引用或覆盖房间 ID、玩家等公共字段。规则回调先验证后修改，不做异步操作。
3. 新增独立卡片和对局组件，在界面注册表增加对应项。CSS 使用游戏专属类名前缀，禁止新增影响其他游戏的全局 `button`、`canvas` 等选择器。注册元数据即可复用现有卡片 → 模式弹窗 → 创建流程，不修改旧游戏组件。
4. 新的实时操作必须使用独立事件命名空间（例如 `newgame:move`），严格检查当前成员和 `room.game`，再调用对应规则。不得复用 `game:move`（这是已有五子棋协议）或 `snake:*`。
5. 新增事件必须沿用服务端身份校验、排队、限流和广播封装。若需 Redis，沿用 `change` 的 CAS 提交路径；不得直接写房间或另建未鉴权 Socket 服务。
6. 新实时游戏的调度器必须只处理自己的游戏 ID、各房间互不阻塞；本次保留贪食蛇原有调度器，新增游戏需要独立接入与并行运行验证。
7. 增加新游戏规则、Socket.IO、双浏览器测试；保留并通过自动化脚本运行所有已有游戏测试，补充新旧游戏并行、非法跨游戏指令、错误模式、再战和关闭隔离。所有测试文件使用现有 `*.test.js` / 浏览器命名规则，CI 会自动发现。必须遵守下方“旧游戏回归执行要求”。

## 旧游戏回归执行要求

- 后续每次新增或修改游戏，旧游戏的所有回归验证必须通过自动化测试脚本执行，包括规则、接口、Redis、多玩家浏览器流程以及需要执行的线上回归。
- 不进行旧游戏的手动点击、手动试玩或人工看截图检查。浏览器操作由 Playwright 等脚本执行，通过自动化断言验证状态、同步、胜负、重连等结果；脚本生成的截图可留作诊断附件，但不能以人工看图作为回归通过依据。
- 发现覆盖不足时，先补充可重复执行的测试脚本并接入现有测试入口，再执行回归。不得以人工检查替代缺失的脚本或失败的断言。
- 测试失败时修复原因并重跑，保留原有测试及断言；全部必过自动化测试成功后才允许上线。失败、跳过、取消、缺失或超时均不得作为通过，不得绕过发布门禁。
- 回归报告注明执行的脚本或命令、通过与失败结果、未覆盖范围；以脚本结果和 CI 记录作为验证证据。

## 必过检查

```sh
npm test
npm run build
npm run test:browser
# 设置独立测试命名空间的真实 Redis 测试会自行清理其测试键
node --env-file=.env.local --test tests/redis.test.js tests/snake-redis.test.js tests/sokoban-redis.test.js tests/creative-redis.test.js
```

Windows 使用本机 Edge 可设置 `PLAYWRIGHT_CHANNEL=msedge`。线上验收设置 `LIVE_BASE_URL=https://www.hearts-ai.top`；测试使用随机账号，不操作日常玩家房间。

CI 在每次 push / PR 执行全套规则、集成、Redis、浏览器测试及生产构建，无按游戏路径跳过。Redis 在 runner 的临时 TLS 容器中运行；不需要生产凭据。`release-gate` 只在前置 `all-game-tests` 完整成功时成功，失败/跳过会明确失败。

Vercel 项目的生产 Deployment Check 必须要求同一提交的 `release-gate` 成功，才给部署分配正式域名。构建可以提前进行，但测试等待、失败或缺失时不切换线上版本。禁止 Force Promote 绕过。门禁设置位于 Vercel 项目而非 `vercel.json`；迁移项目时须重新配置，不能仅复制工作流。详见 [发布门禁](release-gate.md)。

## 已有保护与边界

- 新增模拟游戏的回归证明注册新规则不会替换旧规则、旧房间棋盘和分数不被共享；同时覆盖五子棋胜局/换色再战、贪食蛇推进/合作认输/再战和离开隔离。
- 四个真实 Socket.IO 会话同时运行两款游戏，检查错误事件被拒、各玩家仅收到所属房间状态、关闭一局后另一局继续。
- Redis 测试在同一测试命名空间下保留五子棋房间，并运行贪食蛇跨实例帧、并发推进、重启恢复；验证五子棋未改动且还能继续落子。
- 没有 `game` 字段的历史房间继续按旧版五子棋处理；未知 ID 不再默认为五子棋。现有房间的数据字段及 Redis 命名空间未迁移。
- 默契搬运队独立使用 `sokoban:action`：覆盖八关合法通关、机关门占用、同色箱子限制、双人确认、撤销、过期指令、旧房间隔离；真实 Redis 双实例验证 Socket 广播、并发 CAS 与重启恢复，双浏览器覆盖手机控制、过关、断线与重开，并通过普通界面逐步走完八关、检查两端机关状态和最终共同胜利。`shared/sokoban-mechanics.js` 是前后端共用的机关判定；旧三关快照继续按原关卡数结束，再战升级到八关。
- 星灯维修站与引力四连分别使用 `lights:action`、`gravity:action` 和独立规则/UI/CSS；自动化覆盖三关合作、开关权限、重力翻转与双方判胜、双实例并发、断线恢复、再战和旧游戏房间隔离。
- 模块隔离和测试降低回归风险，不是任意代码变更的零影响保证。游戏仍共享进程、Redis、网络与配额；新增高频游戏仍需检查资源使用、CSS、导入错误和性能，不承诺进程或资源级隔离。
